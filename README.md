# Tutoria — game development learning lab

A reviewable Next.js / React / TypeScript prototype. One illustrative Godot lesson demonstrates the complete student journey; the 17 real tutorials have not been imported.

## Run locally

Requires Node 22.13+ and pnpm 11.19.

```sh
pnpm install --frozen-lockfile
pnpm dev
pnpm build
```

The development URL is http://localhost:3000. The production build creates `out/`, which any static host can serve. `node node_modules/next/dist/bin/next build --webpack` is the direct equivalent if a package-manager wrapper is unavailable. There is no runtime server, database, paid AI provider or student account requirement. Sites is only the private preview host, not an application dependency. Older starter capability helpers remain unused.

## What works

- Search and difficulty/topic filters, responsive library, reusable lesson route.
- Embedded YouTube reference video; chapter and transcript buttons reload the embed at the requested time. Repeated clicks seek again. The normal YouTube controls remain available.
- Written steps, checkpoints, objectives, terminology, troubleshooting, three extension levels, quiz with explanatory feedback, resource links and downloadable text guide.
- Teacher studio: edit every content category, import plain text/SRT/WebVTT, validate and edit complete JSON, preview, explicitly save a browser draft and export/import portable lesson JSON.
- Multiple videos are represented by `media[]`; steps and transcript segments reference media IDs. If a second video is supplied through JSON, a selector appears. No synchronisation is implemented.

## Content and publishing

`content/player-controller.json` holds the sample as ordinary JSON. `lib/lessons.ts` defines the Zod schema, TypeScript type, validated lesson collection and import utilities. All tutorial pages are generated by `app/tutorials/[slug]/page.tsx` using `generateStaticParams`; the shared renderer is `components/tutoria.tsx`.

To add reviewed content: export JSON from Teacher studio; place it in a `content/` directory; import the JSON into `lib/lessons.ts`; add `lessonSchema.parse(importedLesson)` to `lessons`. Give each lesson a unique stable ID and URL slug. Rebuild and deploy the static output. No individual page needs to be copied. Validation checks required content, media references, unique IDs within collections, quiz indices, HTTPS resources and extension levels.

Draft edits are local to the browser and origin. They do not modify the repository or the public collection, and clearing browser data deletes them. Export backups before switching browsers or origins. Save and Preview validate the form; invalid imports leave the current lesson untouched. Edits are not automatically saved. The advanced JSON textarea must be explicitly applied before Save/Preview/export uses it. Future authenticated publishing should replace this deliberate prototype boundary.

The sample is original illustrative teaching text, NOT a transcript of the embedded reference video. Its timestamps are deliberately labelled illustrative. The reference video and thumbnail belong to GDQuest: https://www.youtube.com/watch?v=GwCiGixlqiU. Replace the media, full transcript and reviewed timestamps together before using the lesson in class.

## Architecture for the next stage

Keep student delivery static, with reviewed lesson documents as the source of truth. Add a separate authenticated teacher service only when you are ready to automate authoring. Do not put secrets or draft endpoints into public client code.

Suggested pipeline:

1. Authenticate the teacher; authorise access to their own lessons and videos.
2. Accept and validate a YouTube URL. Store a draft job with an idempotency key.
3. A server-only TranscriptProvider retrieves owner-authorised captions, or accepts a manual upload. Store raw text, timed segments, language, source, video ID and import date. Keep manual source text for audit.
4. A server-only LessonGenerator chunks long transcripts by timestamp, preserving source boundaries. Generate objectives, chapters, instructions, concepts, troubleshooting, extension tasks and quizzes as schema-constrained JSON. Treat transcript text as untrusted data, never as instructions to the authoring service.
5. Validate JSON with the same schema. Require source timestamp/segment references for generated claims, mark uncertain content for review and never invent missing code or resources. Retain model/prompt version and generation provenance outside the student document.
6. Store a draft revision. The teacher compares generated content with the video, corrects it and explicitly approves publication.
7. Publish an immutable lesson revision to the content collection, trigger a static rebuild, and retain the previous revision for rollback. No AI calls occur when students open pages.

Keep provider adapters behind interfaces such as `TranscriptProvider.import(videoId, teacherContext)` and `LessonGenerator.generate(transcript, rubric)`. Use ordinary JSON storage initially; a Git-backed collection is sufficient for 17 lessons. A database, background worker or paid provider is a later choice to discuss, not a current prerequisite. Apply per-job limits and manual retry controls before paid generation is connected.

## Legitimate YouTube caption import

Verified against official documentation on 13 September 2026:

- `captions.list` requires OAuth authorisation and returns caption metadata, not transcript text. Use `part=snippet&videoId=...`, select a language/track and retain its ID. The documented cost is 50 quota units. https://developers.google.com/youtube/v3/docs/captions/list
- `captions.download` requires permission to edit the video and OAuth (`youtube.force-ssl` for the normal owner workflow; `youtubepartner` is for partner workflows). Download the selected track as VTT or SRT. The documented cost is 200 quota units. An API key alone is insufficient. https://developers.google.com/youtube/v3/docs/captions/download
- Implement the OAuth callback and token exchange server-side, bind OAuth state to the teacher session, encrypt refresh tokens, and never ship client secrets or tokens to students. Handle expired authorisation, missing caption tracks and quota errors with an explicit manual fallback. Do not assume every automatically generated caption track will be available for download.
- For now, use an owner-exported caption file from YouTube Studio or paste your transcript. The prototype supports basic timed captions and timestamped plain text. Plain text without times starts at 0:00. Advanced VTT styling/region metadata and overlapping automatic-caption deduplication are not implemented; inspect imported text before publishing. https://support.google.com/youtube/answer/2734698?hl=en

## Future student features

Keep progress records separate from lesson content: `(studentId, lessonId, lessonRevision, stepId, completedAt)`, plus quiz attempts and bookmarks. Stable IDs allow adding accounts later without rewriting lessons. Current completion checks and quiz answers last only for the mounted lesson visit and are not analytics. Classroom camera video can be added as media with role `classroom`; future sync should add explicit timing mappings between media, rather than assuming identical clocks.

## Security and deployment limits

Teacher studio is an openly accessible LOCAL editor, not a secured administration backend. It cannot write shared content or expose credentials. Do not add real publishing APIs until server authentication, per-lesson authorisation, CSRF protection, input limits and an audit trail exist. Student HTML contains quiz answers by design; this is formative practice, not a secure examination system. YouTube playback and thumbnails need an internet connection and may be affected by school network policy or embedding restrictions.

No API keys are configured or required. Any future keys must remain in server-only environment variables without a `NEXT_PUBLIC_` prefix. The static export cannot contain server endpoints; keep authoring in a separate service or deliberately move to a server-capable deployment when that phase is approved.
